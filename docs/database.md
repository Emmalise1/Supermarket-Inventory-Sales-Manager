# Database design

## MySQL (primary, source of truth)

Schema name: `supermarket` (created manually once; tables are generated by
JPA `ddl-auto: update` for local development).

### Tables

**users** - application accounts (RBAC)

| Column | Type | Constraints |
|---|---|---|
| id | BIGINT | PK, auto increment |
| email | VARCHAR(120) | UNIQUE, NOT NULL |
| password_hash | VARCHAR(100) | NOT NULL (BCrypt - never cached, never exposed) |
| full_name | VARCHAR(120) | NOT NULL |
| role | VARCHAR(20) | NOT NULL, enum ADMIN / MANAGER / CASHIER |
| branch_id | BIGINT | FK → branches.id (NULL for admins) |
| active | BOOLEAN | NOT NULL |
| created_at | TIMESTAMP | NOT NULL |

**branches** - physical stores

| Column | Type | Constraints |
|---|---|---|
| id | BIGINT | PK |
| name | VARCHAR(120) | UNIQUE, NOT NULL |
| address, phone | VARCHAR | - |
| active | BOOLEAN | NOT NULL |
| created_at | TIMESTAMP | NOT NULL |

**products** - catalog (branch-scoped stock)

| Column | Type | Constraints |
|---|---|---|
| id | BIGINT | PK |
| barcode | VARCHAR(64) | **UNIQUE**, NOT NULL, index `idx_products_barcode` |
| name | VARCHAR(160) | NOT NULL, index `idx_products_name` |
| category_id | BIGINT | FK → categories.id |
| supplier_id | BIGINT | FK → suppliers.id |
| branch_id | BIGINT | NOT NULL, FK → branches.id, index `idx_products_branch` |
| cost_price / price | DECIMAL(12,2) | price NOT NULL, CHECK price ≥ 0 |
| quantity_in_stock | INT | NOT NULL, ≥ 0 (enforced at service level) |
| low_stock_threshold | INT | NOT NULL |
| active | BOOLEAN | NOT NULL |
| created_at / updated_at | TIMESTAMP | - |

**categories**, **suppliers** - reference data (id PK, unique name for
categories, standard columns).

**sales** - POS sale header

| Column | Type | Constraints |
|---|---|---|
| id | BIGINT | PK |
| sale_number | VARCHAR(40) | UNIQUE, NOT NULL |
| branch_id | BIGINT | NOT NULL, FK → branches.id |
| cashier_id | BIGINT | NOT NULL, FK → users.id |
| total_amount | DECIMAL(12,2) | NOT NULL |
| item_count | INT | NOT NULL |
| status | VARCHAR(20) | NOT NULL |
| created_at | TIMESTAMP | NOT NULL, index |

**sale_items** - line items with price snapshot

| Column | Type | Constraints |
|---|---|---|
| id | BIGINT | PK |
| sale_id | BIGINT | NOT NULL, FK → sales.id (cascade delete) |
| product_id | BIGINT | NOT NULL |
| product_name | VARCHAR(160) | NOT NULL (snapshot) |
| unit_price | DECIMAL(12,2) | NOT NULL (snapshot) |
| quantity | INT | NOT NULL ≥ 1 |
| subtotal | DECIMAL(12,2) | NOT NULL |

**stock_movements** - full inventory audit trail

| Column | Type | Constraints |
|---|---|---|
| id | BIGINT | PK |
| movement_type | VARCHAR(20) | NOT NULL: GOODS_RECEIPT / SALE / ADJUSTMENT |
| product_id | BIGINT | NOT NULL, FK → products.id |
| branch_id | BIGINT | NOT NULL |
| quantity_change | INT | NOT NULL (signed: + adds, − removes) |
| reason | VARCHAR(255) | - |
| user_id | BIGINT | NOT NULL (who did it) |
| created_at | TIMESTAMP | NOT NULL |

### Integrity rules

- **Negative stock is impossible**: sales and adjustments are validated in a
  transaction before any write; the stock update and the movement insert are
  atomic.
- **Unique barcodes** enforced by a unique index (duplicate → 409).
- **Prices come from the database**, never from the client request.
- **Branch scoping**: products, sales, movements and users carry `branch_id`,
  which is what branch-level authorization checks against.

## MongoDB (document-oriented data)

Database: `supermarket`

### Collection `audit_logs`

```json
{
  "_id": "ObjectId",
  "actorId": 2,
  "actorEmail": "manager@supermarket.rw",
  "role": "MANAGER",
  "branchId": 1,
  "action": "PRODUCT_UPDATED",
  "entityType": "Product",
  "entityId": "7",
  "details": "Price changed to 650.00 ...",
  "createdAt": ISODate("...")
}
```

Indexes: `actorId`, `branchId`, `createdAt`.

Written for: login, user create/update, product create/update/deactivate,
sale completed, goods received, stock adjusted, branch/supplier changes.

### Collection `notifications`

```json
{
  "_id": "ObjectId",
  "userId": 3,
  "branchId": 1,
  "type": "LOW_STOCK",
  "title": "Low stock: Bottled Water 1.5L",
  "message": "... has only 8 unit(s) left ...",
  "read": false,
  "createdAt": ISODate("...")
}
```

Indexes: `userId`, `branchId`, `createdAt`.

Notifications are **not** written directly by the business services: services
publish a `DomainEvent` to **RabbitMQ**, and `NotificationConsumer` stores the
notification here asynchronously.

## Redis (cache only)

| Key | Value | TTL |
|---|---|---|
| `product:barcode:{barcode}` | product JSON | 10 min |
| `product:id:{id}` | product JSON | 10 min |
| `dashboard:branch:{branchId}` | summary JSON | 5 min |

No schema - Redis holds disposable copies of MySQL data. Never passwords,
tokens or personal data.
